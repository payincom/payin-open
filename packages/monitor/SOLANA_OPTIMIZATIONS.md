# Solana Adapter 行为说明（2025-10-31）

## 近期调整
- 2025-10-31：移除批量签名请求与恢复缓存逻辑，统一采用顺序扫描，避免在不同 RPC 提供商之间反复切换策略。
- 2025-10-31：保留签名元数据过滤与事件顺序整理，确保返回结果与 EVM 适配器行为一致。

---

## 当前实现要点

### 1. 顺序签名扫描（Sequential Signature Retrieval）
- 逐个 ATA 调用 `getSignaturesForAddress`，使用保守的 `limit=500` 与最多 500 次迭代。
- 自动跳过超出区间的 slot，一旦命中下界或数据耗尽即停止。
- 网络/限流错误会在日志中提示，但不会再次尝试批量或缓存逻辑。

### 2. 签名元数据过滤
- 对 `sig.err !== null` 的交易直接跳过，避免后续 `getTransaction` 的无效调用。

### 3. 统一事件顺序
- 收集到的签名按 slot 升序排序，再批量调用 `getTransaction`（批量大小固定 10），最终返回的 `TransferEvent` 与 EVM/Tron 适配器同样是正序。

### 4. 兼容性与简化
- 不再依赖 provider 对 JSON-RPC 批量的支持，也无需维护运行时缓存状态。
- Monitor 仅需按常规 `BlockScanTask` 调度即可，不会看到批量失败/缓存重建的 WARN。

## 与早期优化的区别
| 功能                         | 现状 | 说明 |
|------------------------------|------|------|
| Batch 签名请求 / 签名缓存     | ❌   | 因各 provider 支持度不一且无法节省费用，统一移除。 |
| 签名元数据过滤               | ✅   | 仍然生效。 |
| 事件顺序对齐                 | ✅   | 保持与 EVM/Tron 相同的升序输出。 |
| getTransaction 批处理（10）  | ✅   | 仅用于减少 HTTP 往返，不影响费用。 |

## 后续观察与可选优化
1. **顺序扫描的性能监控**：关注恢复模式下的耗时与 RPC 请求量，如有需要再根据业务量调整 `limit` 或批次划分。
2. **Provider 统计**：参考 `RPCManager.getProviderRequestStats()`，评估是否需要为 Solana 单独配置更高配额的 RPC。
3. **增量缓存（可选）**：若未来仍需进一步降低请求量，可考虑在顺序模式上构建 lightweight cache，但必须确保不会引入新的失败路径。
