# MCP 客户场景与提示词手册

> 本文从终端客户视角归纳常见问题与操作路径，帮助 AI 助手快速理解不同身份、不同阶段的真实诉求。所有示例均以自然语言对话为主，可直接复制到 Claude / OpenAI Desktop。

## 角色与阶段总览

| 角色 | 典型背景 | 没有 API Key 时 | 已有 API Key 时 | 运营支持重点 |
| --- | --- | --- | --- | --- |
| 业务经理（不熟悉加密） | 负责上线稳定币支付，无链上经验 | 了解名词、申请 API Key、选择链路 | 验证订单收款流程 | 监控回款与退款、生成报表 |
| 技术负责人 | 负责系统集成与测试 | 确定环境、创建测试账号 | 跑通下单/充值接口、处理异常 | 自动化巡检、观测错误率 |
| 运营/风控 | 负责日常监控、异常处理 | 了解权限模型、申请所需 Key | 查询订单与充值明细 | 分析失败原因、输出运营报告 |

## 业务经理（不熟悉加密） <a id="persona-non-crypto"></a>

### 阶段 A：尚未获得 API Key

- **关切问题**：
  - 什么是链、协议、稳定币？
  - 是否必须部署节点？
  - 哪个网络适合测试？
- **建议提示词**：
  - `请用通俗语言介绍 PayIn 支付的链和代币选项，并告诉我测试环境怎么选。`
  - `我该如何在 Admin 后台申请首个 API Key？`
- **AI 拟采取的行动**：
  - 读取 `docs://payin/getting-started`，解释术语。
  - 返回带步骤的 API Key 创建流程。

### 阶段 B：已获得 API Key

- **关切问题**：
  - 如何验证订单创建？
  - 是否需要准备回调？
- **建议提示词**：
  - `请帮我用 create_order 工具创建一笔 10 USDT 的测试订单，并告诉我如何在页面展示二维码。`
  - `我应该如何验证订单状态，从 pending 变成 completed？`
- **AI 拟采取的行动**：
  - 调用 `create_order` 工具，展示响应字段。
  - 指导使用 Webhook 或 `get_order` 轮询。

### 阶段 C：日常运营

- **关切问题**：
  - 如何查看每日新增订单金额？
  - 如何快速定位失败订单？
- **建议提示词**：
  - `请帮我汇总过去 24 小时 orders 的统计数据，并指出 pending 订单的链。`
  - `列出最新 5 笔失败订单的错误原因。`

## 技术负责人 <a id="persona-technical"></a>

### 阶段 A：尚未获得 API Key

- **目标**：确保测试环境一致。
- **提示词**：`请告诉我本地启动 API (localhost:3000) 与 MCP 配置所需的全部环境变量。`

### 阶段 B：已获得 API Key

- **目标**：跑通端到端流程，关注错误处理。
- **提示词**：
  - `请评价我这段订单创建请求 payload 是否符合要求，并使用订单创建校验清单指出问题。`
  - `当订单创建返回 ADDRESS_POOL_EXHAUSTED 时，我应该运行哪些脚本？`
- **建议行动**：
  - 调用 `list_address_pool` 检查可用地址数。
  - 如果必要，指引运行 `POST /api/v1/address-pool/allocate`。

### 阶段 C：上线后

- **目标**：自动化巡检与日志分析。
- **提示词**：
  - `请根据 get_order_stats 的结果生成 Grafana 仪表板的指标建议。`
  - `如果 webhook 失败导致订单未更新，请提供排障 checklist。`

## 运营 / 风控 <a id="persona-operations"></a>

### 阶段 A：申请权限

- **提示词**：`请告诉我运营人员最低需要哪些 API 权限，以及如何在 Admin 中申请。`

### 阶段 B：日常查询

- **提示词**：
  - `查询过去 2 小时内金额超过 1,000 USDT 的订单和充值，并标记所在链。`
  - `请帮我导出 depositReference=vip-user 的所有地址与最近一笔充值时间。`

### 阶段 C：异常处理

- **提示词**：
  - `当用户充值未入账时，请按照充值排障流程指导我操作。`
  - `如果订单显示 ORDER_SERVICE_DISABLED，我应该联系哪些人？`

## 校验与决策清单

### 订单创建校验清单 <a id="order-validation-checklist"></a>

1. `orderReference`：字符串、全局唯一，建议包含业务系统前缀。
2. `amount`：字符串，最多 18 位小数，可用 `<currency>-<integer>` 模式快速识别。
3. `currency`：使用 `list_tokens` 校验符号是否受支持。
4. `chainId`：使用 `list_chains` 校验链是否启用。
5. **地址池**：调用 `GET /api/v1/address-pool/availability`，确认协议剩余地址 > 0。
6. **回调配置**：如需 Webhook，确保公网可访问并校验签名。

### 充值绑定校验清单 <a id="deposit-binding-checklist"></a>

1. `depositReference` 与用户 ID 一致并在业务系统可检索。
2. 协议选择 `evm` 或 `tron`，并与业务场景一致。
3. 地址池是否存在可用地址；检查 `GET /api/v1/address-pool/availability`.
4. 若已存在绑定，确认是否允许复用旧地址。
5. 更新内部备注，记录地址与链列表，便于客服查询。

### 充值解绑决策树 <a id="deposit-unbind-decision-tree"></a>

1. **需要解绑全部地址？** 使用 `POST /api/v1/deposits/unbind` + `depositReference`。
2. **仅解除单个地址？**
   - 提供 `address + protocol`。
   - 如果是误操作，提醒恢复对应的监控任务。
3. **后续动作**：
   - 更新业务数据库中的地址状态。
   - 通知用户重新获取新的充值地址。

## 推荐操作脚本

- **每日运营巡检**：`请帮我执行以下步骤：1) 获取今日订单统计；2) 列出 pending>30min 的订单；3) 总结最常出现的错误代码。`
- **上线前验证**：`检查 address pool、订单服务状态以及 webhook 配置是否就绪。`
- **应急演练**：`模拟 ADDRESS_POOL_EXHAUSTED 场景，并提供恢复脚本。`
